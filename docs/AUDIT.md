# Audit: `fetch_mod_extended_final_complete_ultimo4.py`

**Scope.** The two uploaded files are byte-identical (`md5 3bef02c2055354d91fe3f6e475dd0258`),
so this is a single script of 683 lines. Reviewed against the real inputs supplied:
`mod_downloads.json` (148 entries, generated by Infinity Mod Forge v4.1.0),
`WeiDU.log` (780 component lines, 145 mod folders) and `WeiDUBGEE.log` (16 lines, 4 folders).

**Verdict — is the download safe and correct?** No, on both counts.

It is not malicious, and the intent behind it is sound. But it is built on a
"trust everything, verify nothing" pipeline: it authenticates to third parties it
shouldn't, installs artefacts it cannot identify, extracts them without
containment, and deletes user data when anything goes wrong. Separately, and
independently of security, it installs **at least 40 of your 148 mods into
directory names WeiDU cannot use**, so the resulting tree would not build.

Every finding below is proven by an executable test in
`tests/test_legacy_characterization.py`, which runs the original code. All 13
pass — that is, all 13 defects are real, not inferred from reading.

---

## Severity 1 — Critical

### S1-1 The GitHub token is sent to nine third-party hosts  (test `L5`)
`get_headers()` attaches `Authorization: Bearer <token>` to **every** request,
and `AuthRedirectHandler` only strips it on *redirects*, never on the initial
request. Against your actual manifest that means the token is transmitted to:

```
downloads.weaselmods.net   www.gibberlings3.net   www.shsforums.net
www.pocketplane.net        artisans-corner.com    www.morpheus-mart.com
forums.beamdog.com         baldurs-gate.de        www.baldurs-gate.de
```

Three of those are reached over **cleartext `http://`** (`SirinesCall`,
`FishingForTrouble`, `haerdalisromance`), so the token also crosses the wire
unencrypted. The token the script mints has the `public_repo` **write** scope
(§S3-3), so this is a write-capable credential handed to forum operators.

*Fix:* `net.HttpClient.headers_for()` attaches the credential only to an exact
allowlist `{api.github.com, github.com}`; everything else, including GitHub's own
`objects.githubusercontent.com` asset CDN, gets no credential.

### S1-2 Redirect credential-stripping is defeated by a lookalike host  (test `L6`)
`if "github.com" not in urlparse(newurl).netloc` is a substring test. A redirect
to `https://github.com.attacker.example/steal` **keeps** the `Authorization`
header, because that string contains `github.com`.

*Fix:* exact host-set membership (`net.is_github_auth_host`), plus a refusal to
follow any redirect that downgrades to `http://`.

### S1-3 A manifest `tp2` value becomes a filesystem path, unvalidated  (test `L4`)
`os.path.join(TARGET_DIR, tp2)` with no checks, combined with
`shutil.rmtree(mod_dest_dir, ignore_errors=True)` on the error path. A manifest
entry with `"tp2": "../victim"` therefore **deletes an arbitrary directory
outside the target**. The characterization test demonstrates this destroying a
directory of user data. The manifest is machine-generated by a third-party tool,
so this is a real trust boundary, not a hypothetical.

*Fix:* `naming.safe_component()` rejects traversal, separators, absolute/UNC
paths, NUL, Windows reserved device names and trailing dot/space, and is applied
at manifest load, at plan build, and again at install.

### S1-4 Tar extraction escapes the destination directory  (test `L9`)
`tarfile.extractall()` with no member validation. On Python 3.11 the default
filter is `fully_trusted`, so a member named `../outside.txt` is written outside
the target. `zipfile` silently *sanitises* rather than rejecting, which hides the
attempt instead of failing it.

*Fix:* `archives.safe_extract()` validates every member before writing
(traversal, absolute paths, symlinks, non-regular files), applies
`filter="data"` for tar, enforces entry-count / total-size / compression-ratio
ceilings, and re-audits the extracted tree for escaping symlinks.

## Severity 2 — High

### S2-1 Verification always succeeds  (tests `L1`, `L2`)
```python
def find_tp2_in_dir(mod_dir, tp2_name):
    ...
    for _, filename in tp2s:
        if <fuzzy match>: return True
    return True          # <-- unconditional
```
The final `return True` means **any** directory containing **any** `.tp2` file
passes verification for **any** mod. Consequences, in order of severity:

* `process_mod` returns `SKIPPED` for mods that were never downloaded;
* the "Downloaded & verified" success message is unfounded;
* the post-download audit reports "All mods have valid .tp2 components extracted"
  regardless of what happened;
* the recovery scan can extract mod A's archive into mod B's directory and call
  it verified.

*Fix:* `install.verify_mod_dir()` is strict — see S2-2.

### S2-2 Identity matching is substring-based, in both directions  (test `L3`)
`clean_expected in clean_f or clean_f in clean_expected`, in three separate
places including the function named `scan_archive_for_**strict**_tp2`. Key `ub`
matches `bg1ub`; `bg1` matches `bg1npc`, `bg1ub`, `bg1re`.

WeiDU permits exactly two spellings, and **both appear in your logs**:
`<folder>/<folder>.tp2` and `<folder>/setup-<folder>.tp2`. A strict rule is
sufficient: `tests/test_naming.py` asserts it correctly identifies **148 of 148**
real mods. Strictness costs nothing here.

*Fix:* `naming.matches_tp2()` — exact match against those two forms after
case/punctuation folding, nothing else.

### S2-3 No integrity verification of any kind
No checksums, no signatures, no size validation, no `Content-Type` check. The
only guard is:
```python
if os.path.getsize(dest_path) < 500:   # then look for "<html"
```
so a 3 KB Cloudflare challenge page, a login wall, or a rate-limit JSON body is
accepted as an archive and handed to the extractor (test `L8`). The confusing
downstream symptom is "Unrecognized archive format or corrupt download".

Your manifest carries **zero** integrity metadata — no `sha256`, no version pin,
no release tag. This is the root of the problem and no downloader can fix it
alone; see ADR-0004 and the Phase 2 plan.

*Fix:* stream to `<dest>.part`, hash while streaming, enforce a byte ceiling,
sniff magic bytes, compare against `sha256` when the manifest supplies one, and
only then `os.replace()` into position.

### S2-4 Failure deletes the destination directory
`process_mod`'s `except` branch runs `shutil.rmtree(mod_dest_dir, ignore_errors=True)`
unconditionally — including when that directory pre-existed with hand-edited
content the script did not create. A network blip destroys user work.

*Fix:* `install.install_from_archive()` never deletes the destination. It stages
to `.staging/`, verifies, and only then swaps. An existing directory causes a
`CONFLICT` unless `--force`, and `--force` *moves* it to `.backup/<folder>.<timestamp>`.

### S2-5 Mods are installed under the wrong directory name — 40 of 148
This is a functional defect, found only by joining your two files. The script
uses the manifest `tp2` key as the install directory. In your data that key is
**not** the WeiDU folder name:

* **30 entries differ only in case** — manifest `EET` vs folder `eet`, `EEex` vs
  `eeex`, `bggo` vs `BGGO`, `SoS` vs `SOS`, … On Linux (`ext4`/`xfs`) these are
  different directories, and WeiDU will not find the mod.
* **10 entries differ outright** — `questpack`↔`d0questpack`,
  `HiddenGameplayOptions`↔`a7-hiddengameplayoptions`,
  `c#solaufein`↔`jasteys_solaufein`, `Yvette`↔`l#coi-yvette`,
  `Romance_Expanded`↔`OWRomanceExpanded`, `ISNF`↔`l#isnf`,
  `VerrBG2`↔`l#verrszabg2`, `BloodAndFaith`↔`BLOODFAITH`,
  `JuniperAndTheStoneLeech`↔`l#juniperstone`, and `HPS_PORTRAITS_PROJECT`,
  which has **no catalogue entry at all**.

I believe this mismatch is *why* the fuzzy matching was added — and the fuzzy
matching is what broke verification (S2-1). The two concerns were conflated.

*Fix:* separate them (ADR-0002). The install directory comes from the WeiDU log,
verbatim. Catalogue lookup is exact key → explicit alias file → *suggestion for
a human*. Identity checking stays strict. On your data the join resolves 138/148
exactly, and the suggestion engine proposes the correct catalogue entry for
9 of the remaining 10 (the 10th has no source and is correctly reported as manual).

## Severity 3 — Medium

### S3-1 Unresolvable mods are replaced with an arbitrary GitHub repository  (test `L7`)
```python
search_url = f"https://api.github.com/search/repositories?q={query}+in:name"
found_repo = items[0]["full_name"]
return f"https://github.com/{found_repo}/archive/HEAD.zip"
```
When the repo lookup fails, the script downloads and installs whatever repository
GitHub's search ranks first for a name like `setup-bg1npc` — a name anyone can
register. This is a supply-chain substitution executed silently, with no
notification that the source changed. The same function also mutates owner and
repo names (`-`↔`_`, dropping hyphens) and probes the guesses.

*Fix:* removed entirely. `resolvers.GitHubResolver` queries the exact repository
and reports `MANUAL` with a reason if that fails. Guessing is not resolution.

### S3-2 The landing-page scraper takes the first plausible link on the page  (test `L12`)
No host restriction: `urljoin` happily produces a cross-domain URL, which is then
fetched *with the bearer token attached* (S1-1). An advert, a tracker, or a
mirror can be downloaded in place of the mod.

*Fix:* links are scored, `.exe` and login/captcha links are excluded, and only
**same-site** links are auto-selected. Off-site candidates are reported for review
unless `--accept-offsite` is passed.

### S3-3 The OAuth implementation borrows another vendor's client ID and over-scopes
```python
VSCODE_GITHUB_CLIENT_ID = "Iv1.b507a08c87ecfe98"
... "scope": "public_repo"
```
Two problems. Impersonating Visual Studio Code's registered OAuth client is not
yours to do, and `public_repo` is a **write** scope — a mod downloader never
needs write access to your repositories. The polling loop is also `while True`
with no `expires_in` handling, so it can hang indefinitely; and the manual
fallback uses `input()`, echoing the token to the terminal and scrollback.

*Fix:* device flow removed by default. Credentials come from `--token-file`,
`$GH_TOKEN`/`$GITHUB_TOKEN`, or `gh auth token`; the tool works **anonymously**
too. If you want device flow, `--oauth-client-id` runs it against an app *you*
register, with an empty scope, honouring `interval`/`slow_down`/`expires_in`.
Interactive entry uses `getpass`.

### S3-4 Landing-page URLs with query strings are corrupted  (test `L11`)
```python
clean_url = page_url.split("#")[0].rstrip("/")
if not clean_url.endswith("/"): clean_url += "/"
```
`https://host/f/?do=download&csrf=abc` becomes `…csrf=abc/`. (The `rstrip` is
also immediately undone by the next line.) Gibberlings3 and SHS download links
are query-driven, so this silently breaks them.

### S3-5 Unbounded downloads and no atomicity
`shutil.copyfileobj(resp, out_file)` with no size ceiling — a hostile or
misconfigured server fills the disk. The file is written directly to its final
path, so an interrupted run leaves a truncated archive that the next run treats
as real.

### S3-6 The script always exits 0
`main()` never calls `sys.exit` with a failure code and ignores the collected
`manual_downloads` list entirely (dead code). CI cannot detect a failed run
(test `L13`).

## Reproducibility: an honest limitation

Neither of your WeiDU logs records a single version string — the
`// Name : Version` field is absent on all 796 component lines
(`tests/test_weidu.py::test_supplied_logs_record_no_versions_at_all`), and the
manifest pins nothing either.

So the *inputs* pin nothing, and a first run can only fetch "latest".

**Correction (ADR-0012).** I first concluded from this that the mod set "cannot
be reproduced from these two files". That was too strong. The version is not in
the log or the manifest, but it is in the mod: a WeiDU `.tp2` declares
`VERSION ~v9.2.1~`, and after installing we are holding it. The tool now reads
each installed mod's own tp2 and records the declared version — including for
mods fetched from a forum page, which have no release tag at all.

So the fix is real and two-sided: record `sha256` + `release_tag` + the mod's own
`VERSION` at first successful fetch. The rewrite writes all three to
`Mods/.iemod-fetch-state.json` on every run, and `--emit-pinned-manifest` turns
them into a committable lockfile. What remains genuinely unrecoverable is only
*which* versions were installed originally — going forward, every run is
pinnable. See ADR-0004, ADR-0012 and Phase 2.
